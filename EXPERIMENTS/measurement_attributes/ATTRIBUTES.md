# Measurement concept attributes

Reference for the columns in `output/measurement_concept_attributes.tsv`, generated by
`pull_measurement_concept_attributes.R`. Each row is one **standard concept in the OMOP
`Measurement` domain** (`concept_id`, `concept_name`, `is_panel`); every other column is a
`concept_relationship` of type `Has ...` pulled from that concept, with the **name** of the
related concept (not its id) as the value.

## How an attribute relates to a lab measurement

A lab result stored in the CDM's `MEASUREMENT` table (e.g. "Glucose = 5.4 mmol/L") points to a
single `measurement_concept_id`. That one concept_id is deliberately pre-coordinated: LOINC (and
the mapped SNOMED CT observable entities) built it out of several independent axes — *what* was
measured, *how*, *in what specimen*, *when*, and *on what scale*. The `Has ...` relationships in
`concept_relationship` expose those axes individually, without having to parse the concept name
string. That's what lets harmonisation code group, filter, or validate lab tests by a single axis
(e.g. "all glucose tests regardless of specimen", or "all tests measured in Urine") instead of by
free text.

Most attributes below come from LOINC's 6-axis model (component, property, scale type, system,
time aspect, method) and apply directly to lab tests. The Measurement domain also contains
non-LOINC concepts (mostly SNOMED CT findings/observables, e.g. "White blood cell number -
finding"), which carry a different, larger set of SNOMED CT clinical attributes (finding site,
causative agent, interprets, ...). Those are listed further down since they occur far less often
and describe a *clinical finding* rather than a *lab test protocol*.

## The 6 core LOINC axes (most common)

These are the attributes shown on a concept's Athena page and are present on the large majority
of LOINC lab-test concepts. Frequencies below are the non-missing count out of 308,024 standard
Measurement concepts.

| Column | Relationship | n concepts | Meaning | Relation to the lab measurement |
|---|---|---:|---|---|
| `has_component` | Has component | 81,275 | The analyte/substance being measured (e.g. Glucose, Protein, Hemoglobin) | **What** is being measured — the core identity of the test |
| `has_property` | Has property | 73,153 | The kind of quantity reported (e.g. Mass Concentration, Molar Concentration, Presence, Titer) | **What kind of value** the result represents, independent of unit |
| `has_scale_type` | Has scale type | 69,097 | The measurement scale (Qn = Quantitative, Ord = Ordinal, Nom = Nominal, Nar = Narrative, Doc = Document) | Tells you whether to expect a **number, a category, or free text** in `value_as_number` / `value_as_concept_id` |
| `has_system` | Has system | 68,106 | The specimen / body system the sample was taken from (e.g. Serum or Plasma, Urine, Blood) | The **specimen type** — critical for not mixing e.g. serum and urine glucose |
| `has_time_aspect` | Has time aspect | 68,709 | Timing of the collection (e.g. Point in time (spot), 24 hours, Timed) | Distinguishes a **spot sample from a timed/cumulative collection** (e.g. 24h urine protein vs spot urine protein) |
| `has_method` | Has method | 41,983 | The analytical method or instrument principle (e.g. Test strip, Immunoassay, Automated count) | The **assay method** — same component/system/property can still differ by method (and therefore by expected precision/reference range) |

**2. Hemoglobin [Mass/volume] in Blood** (`concept_id` 3000963)

| Attribute | Value |
|---|---|

| has_scale_type | Qn |

**3. Protein/Creatinine Qualitative in Urine by Test strip** (`concept_id` 1616736)

| Attribute | Value |
|---|---|
| has_component | Protein/Creatinine |
| has_property | Presence or Threshold |
| has_scale_type | Ord |
| has_system | Urine |

Note how examples 1–2 share `has_property`/`has_scale_type`/`has_time_aspect` but differ on
`has_component` and `has_system` — this is exactly what lets code group "all quantitative
mass-concentration spot tests" without hard-coding either analyte. Example 3 shows a
method-specific, ordinal (qualitative) test instead of a numeric one, and this difference is
readable directly from `has_scale_type` (`Ord` vs `Qn`) rather than from the concept name.

## `is_panel`

| Column | Derived from | n concepts | Meaning | Relation to the lab measurement |
|---|---|---:|---|---|
| `is_panel` | `TRUE` if the concept has any outgoing `Panel contains` relationship, `FALSE` otherwise | 2,377 `TRUE` | Whether this concept is a **panel** — an order that bundles several individual component tests (e.g. a respiratory pathogen panel, a metabolic panel) rather than a single result | Panel concepts don't represent one measured value themselves; their `has_component`/`has_property`/etc. describe the *panel* as a whole (often `-`, meaning "not applicable"), while the actual results live on the individual component concepts linked via `Panel contains` / `Contained in panel`. Filtering `is_panel == FALSE` keeps only concepts that represent a single reportable lab result. |

There is no dedicated `concept_class_id` for panels in OMOP — a concept counts as a panel purely
because other concepts are declared as its components via the `Panel contains` relationship.

**Example panel concepts:**

| 706162 | Respiratory viral pathogens DNA and RNA panel - Respiratory system specimen Qualitative by NAA with probe detection | TRUE | Respiratory viral pathogens DNA and RNA panel |
| 701339 | EORTC Quality of Life Questionnaire С30 | TRUE | *(none — a questionnaire panel with no single component axis)* |

## LOINC panel / administrative attributes

| Column | Relationship | n concepts | Meaning | Relation to the lab measurement |
|---|---|---:|---|---|
| `has_answer` | Has Answer | 10,274 | For ordinal/nominal-scale tests, the list of valid result values (e.g. `Detected; Not detected`) | Defines the **allowed value set** for `value_as_concept_id` on qualitative tests |
| `has_module` | Has Module | 25,806 | LOINC/SNOMED grouping module the concept belongs to (e.g. "SNOMED CT core") | Administrative grouping, not part of the test definition itself |
| `has_status` | Has status | 25,806 | Editorial status of the concept (e.g. Active, Defined, Primitive) | Vocabulary-maintenance metadata — not clinical, but useful to flag legacy/deprecated definitions |
| `has_parent_item` | Has parent item | 1,268 | The panel (parent) concept a component test belongs to (e.g. a CBC panel) | The inverse of `is_panel`: a *component* test pointing back up to its panel, mainly used on NAACCR/registry items rather than routine LOINC panels (which use `Contained in panel` instead — see `is_panel` above) |
| `has_start_date` / `has_end_date` | Has start date / Has end date | 1,268 / 23 | Validity window for a temporally-scoped concept | Rare; mostly on registry/EOD (cancer staging) items, not routine labs |

## SNOMED CT clinical attributes (rarer; on non-LOINC Measurement concepts)

These attach mainly to SNOMED CT "observable entity" / "finding" concepts that also live in the
Measurement domain (e.g. "Blood lymphocyte number above reference range"). They describe a
clinical finding derived from a measurement rather than the assay itself.

| Column | Relationship | n concepts | Meaning |
|---|---|---:|---|
| `has_direct_site`, `has_finding_site`, `has_proc_site`, `has_dir_proc_site`, `has_indir_proc_site`, `has_inherent_loc`, `has_relative_part` | Has direct site / Has finding site / ... | 6 – 3,688 | Anatomical site the finding/procedure relates to |
| `has_specimen` | Has specimen | 3,113 | Specimen type collected (SNOMED style, e.g. "Serum specimen") — a SNOMED counterpart to `has_system` |
| `has_interprets` / (inverse `Interprets of`) | Has interprets | 2,757 | Links a finding to the underlying observable it interprets (e.g. "above reference range" interprets "White blood cell count") |
| `has_technique` | Has technique | 1,600 | Technique used to make the observation |
| `has_interpretation` | Has interpretation | 1,550 | Qualitative judgement on the result (e.g. Increased, Decreased, Normal) |
| `has_intent`, `has_causative_agent`, `has_focus`, `has_precondition`, `has_access`, `has_route_of_admin`, `has_surgical_appr`, `has_dir_device`, `has_dir_subst`, `has_process_output`, `has_proc_duration`, `has_asso_visit`, `has_occurrence`, `has_precoord_pair`, `has_permiss_range`, `has_property_type`, `has_type`, `has_unit`, `has_measurement`, `has_variant` | various | 1 – 347 | SNOMED CT procedure/context attributes that occasionally leak into the Measurement domain (e.g. a "procedure" concept classified as Measurement); not meaningful for standard lab tests |

### Example: SNOMED CT clinical finding (not a lab test protocol)

| concept_id | concept_name | has_status | has_module |
|---|---|---|---|
| 132740 | Positive skin test reaction | Primitive | SNOMED CT core |
| 320074 | Blood lymphocyte number above reference range | Defined | SNOMED CT core |
| 320682 | White blood cell number - finding | Defined | SNOMED CT core |

These have no `has_component` / `has_system` / `has_scale_type` — they are clinical
*interpretations* of a measurement, not the measurement's lab-test definition, so they carry
SNOMED CT's finding-oriented attributes instead of LOINC's assay-oriented ones.

## Practical note for this repository

For harmonising Kanta lab data, the 6 core LOINC axes (`has_component`, `has_property`,
`has_scale_type`, `has_system`, `has_time_aspect`, `has_method`) are the attributes worth using:
they let you check that a mapped `concept_id` really matches the intended analyte, specimen, and
result type before accepting a mapping in `LABfi.tsv`. `is_panel` is worth filtering on too —
a Kanta test result should map to a single reportable concept, so a mapping landing on
`is_panel == TRUE` is a signal to look for the correct component concept instead. The SNOMED CT
clinical attributes only appear on non-LOINC Measurement concepts and are not expected on
properly mapped lab tests.
